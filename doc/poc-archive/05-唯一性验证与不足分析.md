# Rust + windows-reactor 唯一性验证与不足分析

> 方法：**从 KeyFlux 代码结构的硬需求反推**，再枚举所有候选方案逐一比对；所有对 `windows-reactor` 的判断**基于其 `public-api.txt`（542KB / 4603 行 / 181 类型声明，master 分支实测）**，非印象。
> 结论先行：**在「UI 框架 = WinUI 3」且「windows-rs 在 UI 进程内」的联合约束下，Rust + windows-reactor 是唯一工程可行方案**；但若放宽定义，存在替代路线（见 §2）。该方案有 **4 项高风险不足**（见 §4），须以 §5 的优化设计对冲，否则「可验收性」不足。

---

## 1. KeyFlux UI 的硬需求（从代码结构推导）

| 编号 | 硬需求 | 代码依据 |

| R1 | 完整 WinUI 控件面（18 视图 / 8 弹窗） | `Views/*.axaml`（18）、`Services/`、弹窗清单 |

| R3 | 亚克力/Mica 分层（画布/侧栏/页面根 Transparent） | 记忆「架构要点」10；`Services/Win32` |
| R4 | 自绘键盘网格 + Viewbox 缩放 | `KeymapPageView`（键格 68×50、Viewbox 缩放） |

| R8 | **集成 windows-rs** | 本次任务要求 |

## 2. 候选方案全枚举

| 方案 | UI 框架 | windows-rs 位置 | R1 控件 | R2 主题可定制 | 工程可行性 | 判定 |
|---|---|---|---|---|---|---|
| **A. Rust + windows-reactor** | WinUI 3（Rust 驱动） | **同进程** | ✅ 覆盖广 | ⚠️ 受限（见 §4） | 中（库很新） | **严格定义下唯一** |
| B. Rust + 其他 Rust GUI（egui/iced/slint/Tauri）+ windows-rs | **非 WinUI** | 同进程 | 自绘 | 自绘 | 高 | ❌ 不满足「框架=WinUI 3」 |
| C. C# WinUI 3 + Rust cdylib（P/Invoke） | WinUI 3（C#） | 跨语言 FFI（同进程） | ✅ | ✅ | 中高 | ⚠️ UI 非 Rust；「集成」程度弱 |
| D. C# WinUI 3 + Rust 侧车进程（IPC） | WinUI 3（C#） | 独立进程 | ✅ | ✅ | 中高 | ⚠️ 同上，且引入 IPC |
| E. Rust 直接手写 WinRT/COM 宿主 Microsoft.UI.Xaml | WinUI 3 | 同进程 | 需自建全部投影 | 需自建 | **极低**（无官方 Rust 投影，等于重写 reactor） | ❌ 实操不可行 |
| F. 纯 C#/C++ WinUI 3 | WinUI 3 | 无 windows-rs | ✅ | ✅ | 高 | ❌ 不集成 windows-rs |

**补充证据**：
- `windows-reactor` = `microsoft/windows-rs` 官方子 crate（`crates/libs/reactor`），README 定位「declarative WinUI 3 library for Rust」；Build 2026 媒体报道微软确立 WinUI 为 Windows 统一原生 UI（**媒体来源，未官方核实**）。
- 社区存在第三方 Rust-WinUI 绑定（如 blog 提到的 `windows-ui`），**成熟度未核实**，不构成可靠替代。
- 除 reactor 外，windows-rs **无其他 WinUI 3 XAML 的 Rust 投影**（`crates/libs` 下只有 reactor 提供 UI 声明层）。

### 2.1 唯一性结论
- **严格定义（windows-rs 代码与 WinUI 3 XAML 同处一个 Rust 进程）**：**A 唯一**。E 理论成立但需自建整套 `Microsoft.UI.Xaml` Rust 互操作，等同重写 reactor，判不可行。
- **宽松定义（产品中只要用到 windows-rs）**：**不唯一**——C/D 亦满足。
- ⇒ 判定：**在你确认的目标下（WinUI 3 框架 + windows-rs 集成）A 是唯一可行解**；C/D 是「同一产品的降级替代」（放弃 Rust 原生 UI）。

## 4. 不足分析（深度）

### 🔴 4.1 主题/皮肤架构无对等物（最被低估的风险）
现有 Claude 皮肤的本质是**覆盖 Avalonia Fluent 主题的资源键**（`App.axaml` 里 `ToggleSwitchFillOn*`/`ComboBoxItemBackground*`/`SystemAccentColor*`/`TextControlBorderBrushFocused` 等 30+ 键，以及 `Claude.axaml` 的 26 画刷/8 阴影/4 半径）。
**reactor 没有 ResourceDictionary/Style/Setter** ⇒ 这条路线**整体不存在**。只能改用 reactor 自身的基元（`ThemeBrush` 8 值 + `Brush/Color/CornerRadius` + `WindowTheme/WindowBackdrop`）。⇒ **换肤架构须从零重建**，且「一套皮肤一份资源字典」的可插拔模式要重设计。

### 🔴 4.2 无阴影 API
`Shadow` = 0 ⇒ 记忆 6.2 中关于卡片阴影的一整套裁定（`ClaudeShadowCard`、悬停四轮结论、Δ亮度量化基线、`0 0 0 N` 描边环教训）**无对等实现**。WinUI 侧通常用 `ThemeShadow`/`CardBackgroundFillColorDefaultBrush`；reactor 未暴露 ⇒ 走 `windows` 原生 interop，或退化为「1px 暖色细环」（记忆里已有此先例，且已论证比外阴影更稳）。

### 🟠 4.3 控件缺口（影响具体页面）
- `WrapPanel`/`UniformGrid` = 0（二者属 Community Toolkit，非核心 WinUI）⇒ **chips 动态换行（R5）** 需自建或 `ItemsRepeater` + 自定义布局。
- `MenuFlyout` = 0 ⇒ 右键/更多菜单可能需组合 `Flyout` 自建。
- 自定义标题栏相关 API 未暴露 ⇒ 主窗自绘标题栏需 `windows-rs` 原生互操作。

### 🔴 4.4 测试与验收能力下降（对你的「仅验收」最关键）
现有 **38 个测试文件**中大量依赖 Avalonia headless/Skia 的**像素/几何/皮肤契约**测试：
`SkinContractTests`、`SettingsCardEffectTests`（Skia 逐字节）、`ScrollBarStylesTests`（滚动条几何解算）、`MotionSmokeTests`、`ActionPageCardStyleTests`、`ModalBlurTests`、`EditorCardHaloTests`、`FocusRingTransferTests`、`ChipRadioTests`、`KeymapPageViewLayoutTests`、`ActionEditorPanelMeasureTests`、三个 `*SmokeTests`。
**reactor 未核实到 headless 测试框架** ⇒ 这批测试**无法等价平移**，回归网出现缺口。⇒ 必须用 §5.D5 的方案重建「可量化验收」。

### 🟠 4.5 其它
- **成熟度**：0.100、2026-04 首发、约 1.2k 下载、官方样例仅 counter / theme-transition；0.x 破坏性变更风险。
- **运行时依赖**：WinUI 3 需 Windows App SDK Runtime（现有为 .NET 自包含）⇒ 交付形态与安装流程变化。
- **构建链**：Makefile / CI（`release.yml`、`analyzers.yml`）/ 部署 `bin/ui` 全改。
- **范式迁移**：MVVM（26 VM + CommunityToolkit.Mvvm）→ React 式 `Component/Message`；无 `Observable`/`Dispatcher`，异步与线程模型需按 reactor 运行时重设（**待核实**）。

## 5. 优化方向（可落地 + 可验收）

### D1 隔离层（Ports & Adapters）—— 对冲「库极新」风险
定义内部抽象 trait：`SettingsApi`、`ConfigStore`、`Theme`、`WindowHost`、`UiPrimitives`；业务组件只依赖抽象，**reactor 仅出现在 `platform/` + `ui/` 薄层**。收益：库升级/替换影响面收敛；纯逻辑可脱 UI 单测。

### D2 主题系统重建（替代 R2）
以 reactor 基元（`ThemeBrush/Brush/Color/CornerRadius/WindowTheme/WindowBackdrop`）构建**自有主题模块** `theme/`：
- 把 Claude 令牌表（Parchment/Ivory/…/Terracotta/Coral）映射为模块常量；
- 保留记忆 5.13 的 **WCAG 对比度基线表**作为**验收判据**（3:1 达标线）；
- 「覆盖 Fluent 键」改述为「显式设定自身画刷」，避免与系统主题耦合。
> ⚠️ 若 PoC 证明 reactor 的画刷表达力不足（如无法逐控件设前景/背景/圆角），则 D1 隔离层下改用 `windows` 原生 interop 补足（**PoC 必须验证**）。

### D3 阴影/描边策略（替代 R2 的视觉层次）
优先：`windows` 原生 `ThemeShadow`（若 reactor 无）→ 回退：**1px 暖色细环**（记忆既有先例，已论证优于外阴影）。验收：像素亮度回读（沿用记忆 6.2 第 19 条方法论）。

### D4 缺口控件自建
- chips：`ItemsRepeater` + 自定义行布局（或自建换行面板）。
- 标题栏：`windows` 原生（`ExtendsContentIntoTitleBar` 等）。
- 菜单：`Flyout` 组合。

### D5 测试三层替代（**保证可验收的核心**）
| 层 | 内容 | 迁移性 |
|---|---|---|
| L1 纯逻辑单测（Rust） | `MarkdownParser`、DTO 往返、i18n 键数、`ConfigSaver` 契约 | **可 1:1 迁移**（本就与 UI 无关） |
| L2 契约测试 | 与 Go 后端 DTO 逐字一致、协议串、i18n 键数 | 可迁移 |
| L3 视觉验收 | **`Windows.Graphics.Capture` 截帧 + 像素亮度/WCAG 回读** | 方法论可平移（替代 Skia headless） |
| L4 行为对照 | 迁移期 Avalonia↔Reactor 同 `config.json` A/B 截图 | 新增，作为过渡期护栏 |

### D6 版本锁定与升级
`Cargo.lock` 入库 + 固定 toolchain + 隔离层 + 冒烟测试；订阅上游 reactor 变更。

### D7 交付形态
`windows-reactor-setup` 随包部署 Windows App Runtime；保持部署路径 `bin/ui` 不变，降低部署脚本改动面。

### D8 分阶段门禁
见 `03-分步实施计划.md`；每阶段产出**验收证据包**（命令 + 输出 + 截图/像素数据 + SHA256）。

## 6. 可落地性 / 可验收性设计（因验收由你承担）

1. **先 PoC 后承诺**：Phase 1 用 PoC 逐项判定 §3 表格中所有 ⚠️/❌，把「待核实」清零后才进入开发。
2. **每个可交付单元附验收清单**：可执行命令 + 期望输出 + 证据文件（截图/像素表/SHA）。
3. **量化判据优先**：对比度、Δ亮度、键数、往返保真——沿用你既有的「厌恶自我报告式成功」偏好。
4. **回退点明确**：迁移期双工程并存，Makefile 切换点最后落地且需你确认。
5. **风险早暴露**：PoC 必须覆盖 材质 / 主题画刷表达力 / 自绘网格 / chips / 弹窗 / 截帧测试 六项。

## 7. 结论与建议

- **唯一性**：在「WinUI 3 框架 + windows-rs 进程内集成」约束下，**Rust + windows-reactor 是唯一工程可行方案**（已证实；替代方案均需放弃其中之一）。若你愿意放弃「Rust 原生 UI」，C/D（C# WinUI 3 + Rust）是唯一可行替代，可作为风险对冲记录在案。
- **主要不足**：主题/皮肤架构无对等物（🔴）、无阴影 API（🔴）、测试验收网缺口（🔴）、控件与标题栏缺口（🟠）、库成熟度低（🟠）。
- **建议**：**先做 Phase 1 PoC** 验证上述 6 项；PoC 通过则按 D1–D8 执行；若 D2/D3 证明 reactor 表达力不足，则在同一隔离层下引入 `windows` 原生 interop 补足（仍属方案 A，不改变唯一性结论）。
